# P3-1 架構與安全性盤點（2026-11-25）

基準 main 0204a816053548ffb4e14f5501e8a7b7fdf910eb。P2 已結案；P2.5 金鑰隔離驗證與中度依賴驗證仍未結案。本文件為唯讀靜態盤點，未探測正式資料、未變更規則、未重跑壓測。只允許隔離設計與測試先行，正式改版在 P2.5 結案與各階段 CI 通過後分步核准。維持 Spark、GitHub Pages、現有三主題、遊戲計分規則與操作流程。

## 現行資料流與權限邊界

GitHub Pages 靜態前端 app.js → Firebase Auth 匿名 UID / App Check → Firestore Security Rules → rooms 父文件、players 與 votes 子集合。SDK 瀏覽器版 11.10.0；測試端 Firebase 13.4.0，Rules 測試使用 demo 專案，不等同實際雲端 App Check。App Check 強制狀態以 P2 使用者驗收紀錄為據。主持人亦是玩家，20 人包含主持人。

| 資源／操作 | 現況（依 firestore.rules、app.js 900–1135） | P3 目標 |
| --- | --- | --- |
| 房間 | 登入者可精確讀取，不可列表；房主建立與有限狀態轉移 | 僅提供入房所需資訊，會員／房主讀取完整房間 |
| 玩家名單 | 登入者可讀；lobby 自建 UID 文件，不可修改或刪除 | 會員讀取；原子入房、硬上限、重連不重複 |
| 投票 | 登入者可讀；會員於當前 voting 題目一次性建立自己的文件 | 揭曉前非本人不得讀內容；會員只能取得公開進度 |
| 遊戲狀態／分數 | 房主專屬轉移，部分形狀與數量檢查；結算由房主瀏覽器計算 | 伺服器時間、不可重複結算、可信度邊界清楚 |
| 刪除／管理 | 客戶端拒絕；管理員另行操作 | 保留唯讀掃描、人工審核、個別遞迴刪除流程 |

現行入房先讀房間與全名單再建立 player；父文件與主持人文件分開建立，非原子。現有各端透過 votes 查詢監聽整批投票，主持人另每 2 秒最多一次、每題最多 24 次聚合備援；結算另讀 server votes。不可直接收緊讀權限而不更新加入、計數與結算協定。現有時間欄位採客戶端整數，Rules 未以 request.time 驗證截止；房主揭曉結果是結構檢查而非驗證演算法。前端最少兩人與 20 人上限未構成伺服器端不變量。以上均為靜態讀碼結論，待 emulator 驗證。

## 分階段交付（先隔離，後部署）

- P3-2：設計版本化入房協定。優先原子交易、固定最大容量與 getAfter 驗證雙向入房不變量；主辦者一併占名額。先驗證不可跳過關聯寫入、同 UID 重連、20/21 人、並行搶最後一位、遊戲開始與入房競爭、初始 host/room 原子性、舊房相容。評估以最小公開邀請資料分離完整房間與名單；不能假定 Rules 能單靠查詢結果計算容量。若交易成本或 Rules 限制不符，先保留舊版而非放寬規則。
- P3-3：在 P3-2 協定上加入可信時間、每 UID 有界操作、重複投票拒絕與房間生命週期檢查；伺服器時間採 request.time / serverTimestamp 協定並保留提前揭曉與可接受的截止寬限。匿名新 UID 或跨 IP 濫用無法由現有 Rules 可靠完全阻擋；不承諾免費架構能提供硬性全域限流。
- P3-4：拆分私有投票與公開進度；每個計數增量與不可覆寫投票必須原子綁定，避免任意增票及跨題。會員本人、其他會員、非會員、房主與各階段讀取矩陣逐項驗證。若由房主瀏覽器結算，仍存在房主讀票及計分信任界線；完全對房主保密及可信計分需要不同受信任架構或重新設計協定。先評估，不新增付費服務，不更改計分公式。
- P3-5：隔離測試背景分頁、失聯、同 UID 重連、主持人重新整理、重複事件、逾時提交、提前揭曉與結算競爭；不得讓舊題回應污染新題。
- P3-6：保留 7/30 天政策、唯讀預覽及人工遞迴刪除；查核 Firebase 配額及異常彙總，避免個資。無自動刪除；不開 Blaze。
- P3-7：emulator 2/5/10/15/20/21 人及並行案例。以固定測試題、每題 30 秒、至少 6 題為基本場景；記錄成功／拒絕數、P50/P95 延遲、重連、結算一致、讀寫量、錯誤與失敗場景。目標正常網路 95% 更新 ≤3 秒、無非法加入、無重複結算。emulator 不代表正式雲端延遲；實機結果另外標記。正式測試需另行允許測試資料寫入。

## 基線與發布控制

P2 正式六題由使用者回報約 3、1、1、1、1、1 秒，平均 1.33 秒，6/6 達標；並非 20 人壓力結果。現有 39 項 Rules emulator 斷言已於先前 CI 通過。12 題主持人備援每場最多 288 次聚合查詢，不等於 288 次完整計費讀取；實際計價依索引及最小計費。既有 30 天 API 請求指標不能當成 Firestore 文件操作或配額基線；後續須以隔離測試及 Firebase 用量頁建立讀、寫、刪除實測基準。

新增各階段 PR 先 emulator、UI、計分與相容性回歸；以協定版本明確分流，凍結舊房或完成既有房間後再遷移。規則發布與 Pages 前端發布不同步，需獨立部署計畫、維護窗口及回滾；禁止先部署破壞現有遊戲的單側變更。無測試證據不合併功能改動。

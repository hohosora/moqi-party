## 第一、二批：隔離入房協定與測試

tests/p3-lab/admission.rules 是 **僅供 emulator 使用** 的替代規則，不由 firebase.json 部署。獨立的 p3LabInvites 公開精確查詢文件僅包含 phase、count、seats（座位占用布林值，不含 UID）；p3LabRooms 和 members 只允許會員讀取完整資料（本人可檢查自己的會員文件）。禁止集合枚舉、非會員讀取、修改既有會員或刪除。主持人占第一個席位；建立 gate、room、member 以 batch 原子提交；加入以交易取得唯一空席。規則用 getAfter 對同一筆會員與計數寫入互相驗證。計數與占用座位數相符且不超過 20。房主從 lobby 開始投票後關閉新入房；同 UID 可重連，前提為匿名身分仍存在。

這不是現有遊戲的新版資料協定：不包含問題、投票、計分、揭曉、UI、正式舊房遷移或跨裝置驗證。需先檢查 emulator CI；通過後設計真實房間版本化、相容橋接、回滾及受控發布，不能直接把隔離 Rules 替換現行 Rules。座位公開查詢會顯示房間是否存在及容量，仍不等於全域防掃描或限流。

測試：2、5、10、15、20 個實際 emulator member 文件，並行搶最後名額、21 人拒絕、重連、非會員讀取拒絕、單側／越權寫入、開始與加入競爭；非 20 人正式遊戲壓測。啟動命令：`npx --no-install firebase emulators:exec --project demo-moqi-party-p1 --only firestore "node tests/p3-lab/admission-emulator.cjs"`。GitHub Actions 分別執行隔離測試及唯讀 npm audit/outdated。CI 尚待回報；不以提交成功代替驗收。

## 第三、四、五批：下一個關卡

1. 第一、二批通過後：設計可信時間與作答寬限、逐 UID 有界操作和可測的匿名濫用防護。不得以瀏覽器時間或單 UID 限制宣稱全域限流。
2. 私密投票及公開進度協定需同一原子寫入綁定，逐階段及角色驗證；主持人若仍讀票、在瀏覽器結算，不能宣稱防惡意主持人或完全可信計分。
3. 斷線恢復、提前揭曉、結算競爭、重複事件，需在正式協定選定後測試。
4. 依序 2/5/10/15/20/21 人遊戲測試，包含每人作答、每輪結果一致性及延遲。隔離入房測試不等於多人投票壓測。正式雲端測試另需受控環境和權限。

## 初步資源模型（非帳單／實測）

現行每位玩家都訂閱本輪完整 votes，理想化 N 位都投票且所有 N 位持續監聽，會有 N×N 筆投票文件變更交付／輪（20 人時約 400；12 題約 4,800）。主持人結算每輪另外讀取最多 N 筆投票；12 輪約 240。主持人備援聚合每輪最多 24 次／12 輪最多 288 次查詢，依實際索引和最低計費計算。尚不包含初始讀取、重新連線、Rules 額外存取、房間、名單監聽、寫入及重試。上述交付數非帳單精準讀取數。改用單一公開計數也可能每次作答向 N 位訂閱者交付更新，不可直接聲稱讀取量變成 O(N)。應以 emulator 事件計數與實際 Firebase Usage 交叉核對，保留免費方案與用量停止條件。
